01

System architecture

Phase 2 working document
Internal, not for the team pack
Machines find, read and assemble. People decide.
Every gate in Phase 1 stays human. Automation removes the typing, the searching and the checking, not the judgement or the sign off.
A. SOURCES
42+ platforms, six tiers
eTenders, SANRAL, provincial, municipal, aggregators, donor funded. Mixed RSS, HTML, email.
B. INGESTION
n8n workflows
One workflow per ingestion method. Scheduled polls, dedupe on hash, normalise to one record shape.
C. STORE
Postgres and file store
Structured records in SQL, source documents on disk or object storage, one folder per tender.
D. EXTRACTION
OCR then Claude
Textract or Azure Document Intelligence for layout and text. Claude turns text into the returnables checklist and requirements matrix.
E. WORK SURFACE
Airtable tracker
The pipeline as views: by stage, by owner, by closing date. Gate buttons write back to SQL.
F. OUTPUT
Packs and checks
Pre filled forms, assembled returnables set, completeness report before upload.
HUMAN IN THE LOOP, BY STAGE
01Machine captures and logs. Owner assignment stays manual, one tender one owner.
02Machine scores the go or no go criteria it can see. The decision and the signature stay human.
04Machine drafts the checklist and matrix. Owner verifies every line before work starts.
05Machine checks Vault expiry dates against the closing date and raises the alert.
07Machine suggests rates from history. Pricing and margin remain the owner's call.
10Machine pre fills standing details and assembles in tender order. Signatures stay wet ink.
13Machine runs the completeness scan. Submission is still a person clicking upload.
FEEDBACK LOOP, STAGE 15
Outcome recorded

Rate Library

RULES THAT DO NOT BEND
No automated submission. Ever.
No machine written price.
Extraction output is a draft until a person signs it.
Source documents are stored unaltered.
Every automated action is logged with a timestamp.
If the automation is down, Phase 1 still runs by hand.
02

Discovery layer

Replaces the manual watchlist
Stage 00 and 01
Four ingestion methods cover every platform in the reference. Build them in this order: the RSS feeds are a weekend, the scrapers are the long tail.
METHOD 1, EASIEST
RSS poll
n8n RSS node on a schedule. No parsing, no breakage, no blocking.
TenderBulletins, TenderFlow, SA-Tenders
HOURLY
METHOD 2
Email alert parse
Subscribe the shared mailbox to every platform that offers alerts. n8n IMAP node reads, Claude extracts the fields.
Aggregator alerts, OnlineTenders, client and main contractor invitations
ON ARRIVAL
METHOD 3
HTML scrape
n8n HTTP request plus CSS selectors. One workflow per site, versioned, with a failure alert when the selector stops matching.
eTenders, SANRAL, Gauteng DID, municipalities.co.za, ProTenders, Mogale City
TWICE DAILY
METHOD 4, LAST RESORT
Manual check, logged
Sites behind logins or javascript that resists scraping. The person still checks, but records the check in the tracker so coverage is visible.
Portals requiring authentication, donor platforms
WEEKLY
PIPELINE INSIDE EACH WORKFLOW
1. Fetch
Poll on schedule
→
2. Normalise
One record shape
→
3. Dedupe
Hash of number plus client
→
4. Filter
Keywords and CIDB grade
→
5. Create
Row in tracker, alert to owner
FILTER KEYWORDS, FROM THE PLATFORMS REFERENCE
road maintenance, road rehabilitation, reseal, asphalt, bitumen, cold mix, hot mix, paving, patching, pothole repair, surfacing, civil works, earthworks, stormwater, culvert, drainage. Region filter on Gauteng, North West, Northern Cape and Eastern Cape. Grade filter on CIDB 5CE and above.
ALERT ROUTING
Match on all filters, closing more than 14 days out. Daily digest to the shared mailbox.
Match on all filters, closing inside 14 days. Immediate Teams message, tagged urgent.
Partial match. Weekly review list, no alert.
Scraper failure or zero results where results are expected. Alert to you, not the team.
THE FAILURE THAT MATTERS
A silent scraper is worse than no scraper. If a workflow returns nothing for two consecutive runs on a site that is normally active, treat it as broken and fall back to the manual check until it is fixed.
03

Document capture, stage 04

OCR and extraction
Highest value automation
Deconstructing a 300 page tender by hand is where two days disappear. This chain turns the document into a checklist and a matrix in under ten minutes, then hands it to the owner to verify.
STEP 1
Ingest
Tender pack lands in the job folder. Watcher fires. Original stored unaltered.
→
STEP 2
Split and classify
Break into sections. Tag each as conditions, specification, BOQ, returnable form or annexure.
→
STEP 3
OCR
Textract or Azure Document Intelligence. Tables kept as tables. Page numbers preserved for traceability.
→
STEP 4
Claude extraction
Structured output against a fixed schema. Every field carries the page it came from.
→
STEP 5, HUMAN
Owner verifies
Line by line against the source page. Nothing proceeds on unverified extraction.
WHAT CLAUDE EXTRACTS
Tender number, client, description, closing date and time
Briefing session, compulsory or not, date and venue
Query deadline
Every returnable form, with its reference and whether it is mandatory
Eligibility requirements, CIDB grade and class, B-BBEE requirement
Bond, guarantee and insurance requirements
Evaluation criteria and weightings
JV and local content requirements
Submission method, address or portal, format rules
TWO OUTPUTS, BOTH DRAFTS
Returnables checklist
One row per required document, with source page, mandatory flag, where it comes from and current status. Writes straight into the tracker.
Requirements matrix
One row per requirement, with the evidence that satisfies it and the gap where none exists. Feeds the go or no go tree at gate 1.
Both are marked DRAFT until the owner signs off. The tracker will not advance past stage 04 while a draft flag is set.
CONFIDENCE HANDLING
Found and unambiguous. Written as normal, still verified.
Found but ambiguous or conflicting between sections. Flagged for the owner with both readings and both page numbers.
Not found. Left empty and listed as an open question, never guessed.
TEST BEFORE TRUST
Run the chain against twenty past tenders we already deconstructed by hand. Compare line by line. Do not put it in front of the team until the checklist matches on every mandatory returnable.
04

Data model

Postgres is the record
Airtable is the view
One rule keeps this sane. SQL owns the truth, Airtable owns the interface. Anything typed in Airtable syncs back to SQL, nothing lives only in Airtable.
tenders
id, tender_no, client, title, sector, region, value_band, closing_at, briefing_at, query_deadline_at, source_platform_id, stage, owner_id, status, created_at
The spine. One row per tender, from capture to outcome.
platforms
id, name, url, tier, ingest_method, cadence, last_success_at, last_result_count, health
The 42 platforms, with the health field that catches a silent scraper.
returnables
id, tender_id, reference, name, mandatory, source_page, satisfied_by, doc_id, status, verified_by, verified_at
Written by extraction, closed out by the owner. Drives gate 2.
vault_docs
id, category, name, file_path, issued_at, expires_at, issuing_body, replaces_id, current
A nightly job compares expires_at to every open closing date and raises the alert.
rate_items
id, description, unit, rate, priced_at, tender_id, client, region, won, escalation_index, notes
The Rate Library. Query by description and region, escalate to today, suggest at stage 07.
documents
id, tender_id, kind, file_path, checksum, ocr_status, pages, uploaded_by, uploaded_at
Every file, with a checksum so an altered original is detectable.
gates
id, tender_id, gate_no, decision, decided_by, decided_at, reason, evidence_url
The audit trail. A tender cannot change stage without the matching gate row.
outcomes
id, tender_id, result, our_price, winning_price, winner, awarded_at, lessons, debrief_by
Closes the loop. Price gap analysis becomes possible the day this table has rows.
AIRTABLE
VIEWS
MY TENDERS
Filtered to owner, sorted by closing date, T minus days as a formula field.
GATE QUEUE
Everything waiting on a signature, grouped by gate number.
EXPIRY WATCH
Vault documents expiring before any open closing date. Should always be empty.
05

Assembly and submission check

Stages 10 and 13
Where bids die on technicalities
STAGE 10
Pre fill and assemble
1. Map the fields
Claude reads each returnable form and maps its fields to our standing company record. Company name, registration, VAT, CIDB, B-BBEE, banking, contact, addresses.
2. Fill what is standing
Fill only fields with one correct answer that never changes per bid. Anything judgement based stays blank by design.
3. Print for signature
Output a print pack with signature and initial points marked. Wet ink stays wet ink.
4. Assemble in tender order
Scanned signed pages plus the born digital documents, merged in the order the tender specifies, indexed and page numbered.
WHAT WE DO NOT PRE FILL
Prices, rates, programme dates, method statements, declarations of interest, local content commitments, anything requiring a signature. A pre filled declaration nobody read is a fraud risk, not a time saving.
STAGE 13
Completeness check before upload
THE SCAN, RUN AGAINST THE VERIFIED CHECKLIST
01Every mandatory returnable present, matched by reference not by filename
02No blank page where a form should be, no page scanned upside down
03Signature detected on every page flagged as requiring one
04Every Vault certificate valid at the closing date, checked again at the last moment
05BOQ totals in the submitted file match the signed gate 3 figure
06File format, file size and naming comply with the portal rules extracted at stage 04
07Gate rows 1 to 4 all present and signed in the database
OUTPUT
Green report
One page, all checks passed, filed with the submission proof.
Blocking list
Anything failing, with the page reference. Upload stays closed until it clears.

Build sequence

Built by you, hands on
Each step ships something usable
Ordered by value divided by effort, and by what unlocks what. Nothing here needs the step after it to be useful on its own.
01
Database and tracker
Postgres schema from artboard 04, Airtable synced on top, Phase 1 data typed in.
Unlocks everything. Every later step reads or writes this.
1 to 2 weeks
02
Discovery, RSS and email first
Three RSS feeds and the shared mailbox parser. Dedupe, filter, write to tracker.
Immediate coverage gain with no scraping fragility. Proves the record shape.
1 week
03
Vault expiry watcher
Nightly job comparing vault_docs.expires_at against every open closing date.
Smallest job on the list, removes the most common disqualification.
2 days
04
Document capture chain
OCR plus Claude extraction against a fixed schema, validated on twenty past tenders.
The big one. Two days of owner time back per tender.
3 to 4 weeks
05
Scrapers, tier by tier
eTenders and SANRAL first, then Gauteng DID, then the municipal aggregators.
Long tail. Add one site at a time, each with a health check.
Ongoing
06
Rate Library queries
Load historical priced items, add escalation, suggest rates at stage 07.
Needs outcome rows to be worth much. Value compounds over a year.
2 weeks
07
Pre fill and completeness check
Field mapping, print pack, and the stage 13 scan against the verified checklist.
Depends on step 04. Build it once extraction is trusted.
3 weeks
Phase 2 opens when Phase 1 has run a full quarter without a missed gate.
